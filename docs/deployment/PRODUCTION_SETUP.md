# ARC — Production Setup Guide (M8.2)

End-to-end procedure to take the frozen ARC baseline into production. Nothing in this
guide changes architecture: the VPS remains the sole trading authority and the companion
remains the control plane.

## 0. Prerequisites

- Production control-plane project provisioned (see `supabase-cutover.md`).
- VPS provisioned with Node.js, PM2, TLS reverse proxy, and a persistent data volume.
- One shared authority signing key generated by the operator: `openssl rand -hex 32`.

## 1. Secrets

| Secret | Where it lives | Notes |
| --- | --- | --- |
| `ARC_AUTHORITY_SIGNING_KEY` | Companion server env **and** VPS env | Identical on both sides. Never committed, never logged, never shown in the UI. |
| `SUPABASE_SERVICE_ROLE_KEY` | Companion server env, VPS env | Server-only. Never in a browser bundle. |
| `ARC_VPS_API_TOKEN` | Companion server env, VPS env | Bearer token for companion → VPS reads. |
| Wallet / exchange credentials | VPS secret store only | Never referenced by this repository. |

Verification on the companion: `/system` → **Authority Signing** shows
`Status: Configured`, `Source: Server Environment`, and a `Last Verified` timestamp once
the VPS has sent its first signed message. The value itself is never displayed.

## 2. Environment provisioning

1. Companion: copy `.env.production.example` into the hosting provider's secret store.
2. VPS: copy `.env.vps.example` to the VPS environment file (outside the repository).
3. Fill every variable marked `required`. `[SHARED]` values must match byte-for-byte.
4. Start each process. A missing or invalid required variable aborts startup with an
   operator-readable error naming the variable, the problem, the action and the recovery.

## 3. Control-plane cutover

Follow `supabase-cutover.md`. Set `ARC_REQUIRED_SUPABASE_URL` to the production URL; a
mismatch with `SUPABASE_URL` fail-closes every mutation.

## 4. Operator ownership

1. Register the first operator account — it becomes OWNER.
2. Confirm on `/ownership`, then finalize. Registration is permanently disabled afterwards.

## 5. Authority registration and PM2

1. Start the engine under PM2 with `ENGINE_MODE=OBSERVE`.
2. The engine registers itself and begins signed heartbeats.
3. `/engine-registration` must report `ACTIVE` with a fresh heartbeat and a stable runtime identity.
4. Run the PM2 restart validation in `M8_PM2_VALIDATION.md`.

## 6. Configuration activation

1. Edit and save the execution profile on `/execution-profiles`.
2. Publish. The version is immutable and hashed.
3. The VPS accepts and confirms it; `/configuration` transitions
   `NOT_PUBLISHED → PENDING → ACCEPTED → ACTIVE`.
4. `ACTIVE` is only ever set from a live authority confirmation.

## 7. Qualification

Open `/qualification` and confirm, in order:

1. Testnet qualification gates (M7.7)
2. Live authority gates (M7.8)
3. Activation checklist (M7.9)
4. Startup evidence — nine steps (M7.10)
5. Mainnet readiness gate — eight domains (M8.0)

All gates must be green before `ENGINE_MODE=ARMED`.

## 8. Deployment checklist

`/deployment` renders the thirteen-item evidence-based checklist. Every item must be
satisfied by verified evidence, not by an operator override — no override path exists.

## 9. Go live

1. Set `ENGINE_MODE=ARMED` in the VPS environment.
2. `pm2 reload arc-engine --update-env`.
3. Watch `/operations` for incidents and `/trade-monitor` for the first lifecycle.

## 10. Rollback

`pm2 reload arc-engine --update-env` with `ENGINE_MODE=OBSERVE`, then follow
`../operations/BACKUP_AND_RECOVERY.md`. Configuration rollback re-publishes an earlier
immutable version; recovery never duplicates intents, orders, settlements or ledger records.
